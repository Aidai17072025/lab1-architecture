# \# Library Management System

# 

# \## Выбранная предметная область



# Library Management System — веб-приложение для управления библиотекой, каталогом книг, читателями, выдачами и бронированиями.



# \## Описание системы

# 

# Library Management System — веб-приложение для автоматизации работы библиотеки и учёта книг. Читатели могут искать книги в электронном каталоге, просматривать информацию о них и бронировать доступные экземпляры. Библиотекари управляют каталогом, регистрируют выдачу и возврат книг, а также контролируют доступность экземпляров. Администраторы создают учётные записи пользователей и назначают им соответствующие роли. Система хранит информацию о книгах, авторах, читателях, бронированиях и истории выдач в единой базе данных. Использование приложения позволяет отказаться от бумажных журналов и уменьшить количество ошибок при учёте книг. Разграничение прав доступа обеспечивает выполнение каждой операции только уполномоченными пользователями.

# \## Сущности системы

# 

# 1\. \*\*User\*\* — пользователь библиотеки, его данные и роль.

# 2\. \*\*Book\*\* — книга с названием, ISBN и описанием.

# 3\. \*\*Author\*\* — автор книги.

# 4\. \*\*BookCopy\*\* — конкретный экземпляр книги.

# 5\. \*\*Loan\*\* — информация о выдаче книги читателю и её возврате.

# 6\. \*\*Reservation\*\* — бронирование книги читателем.

# 

# 1\. Регистрация пользователя.

# 2\. Авторизация пользователя.

# 3\. Поиск книг в каталоге.

# 4\. Просмотр информации о книге.

# 5\. Бронирование доступной книги.

# 6\. Отмена собственного бронирования.

# 7\. Выдача экземпляра книги читателю.

# 8\. Регистрация возврата книги.

# 9\. Добавление новой книги в каталог.

# \## Обоснование архитектурных решений

# 

# \### 1. Почему выбрана трёхуровневая архитектура?

# 

# В Library Management System используется трёхуровневая архитектура: Frontend (React), Backend (NestJS) и база данных PostgreSQL. Такое разделение позволяет независимо изменять интерфейс, серверную логику и хранение данных. Если бы браузер напрямую подключался к базе данных, это создало бы угрозу безопасности и усложнило контроль доступа.

# 

# \### 2. Какие данные хранятся в базе данных, а какие у клиента?

# 

# В PostgreSQL хранятся пользователи, роли, книги, авторы, экземпляры, бронирования и история выдач. На стороне клиента временно хранятся данные интерфейса, результаты поиска и токен авторизации. Если хранить основную информацию только в браузере, она может быть потеряна или изменена пользователем без контроля сервера.

# 

# \### 3. Где применяется принцип Stateless?

# 

# Backend NestJS использует принцип Stateless: сервер не хранит пользовательские сессии в оперативной памяти между запросами. Каждый защищённый запрос содержит токен авторизации, по которому сервер определяет пользователя и его права. Это позволяет обрабатывать запросы на разных экземплярах Backend без привязки пользователя к одному серверу.

# 

# \### 4. Почему выбран модульный монолит?

# 

# Для Library Management System выбран модульный монолит NestJS, поскольку система имеет ограниченный набор функций и может разрабатываться как единое приложение. Модули авторизации, книг, бронирований и выдач логически разделены, но развёртываются вместе. Если количество пользователей и нагрузка значительно увеличатся, отдельные модули при необходимости можно выделить в самостоятельные сервисы.

# 

# \### 5. Какие проверки выполняются на сервере?

# 

# Backend проверяет подлинность пользователя, его роль, корректность данных и доступность экземпляра книги перед бронированием. Например, читатель не может назначать роли другим пользователям, а библиотекарь не должен выдавать уже занятый экземпляр. Эти проверки нельзя оставлять только в React, поскольку пользователь может изменить запрос или отправить его напрямую к API.









# \## Анализ рисков

# 

# | Риск | Последствие | Способ снижения риска |

# |---|---|---|

# | Недоступность базы данных PostgreSQL | Пользователи не смогут искать и бронировать книги, а библиотекари — регистрировать выдачи и возвраты. | Регулярное резервное копирование, мониторинг состояния базы данных и восстановление работы при сбоях. |

# | Одновременное бронирование одной книги двумя читателями | Два читателя могут получить подтверждение бронирования одного экземпляра книги, что приведёт к конфликту. | Использовать транзакции PostgreSQL и ограничения целостности, чтобы один экземпляр нельзя было забронировать дважды. |

# | Несанкционированный доступ к системе | Злоумышленник может получить доступ к чужим бронированиям, данным пользователей или административным функциям. | Использовать HTTPS, хэширование паролей, проверку токенов, разграничение прав RBAC и ограничение попыток входа. |

# | Перегрузка сервера NestJS | При большом количестве одновременных запросов поиск и бронирование книг будут выполняться медленно. | Использовать индексы PostgreSQL, оптимизировать запросы и при необходимости увеличивать серверные ресурсы. |

# | Ошибка в работе модуля бронирований | Бронирование может не сохраниться или получить неправильный статус. | Проверять входные данные, использовать транзакции, журналирование ошибок и автоматизированные тесты. |

# 

# \## Вывод по анализу рисков

# 

# Наиболее важными рисками для Library Management System являются недоступность базы данных, конфликтующие бронирования и несанкционированный доступ. Для снижения этих рисков используются резервное копирование, транзакции PostgreSQL, защищённое HTTPS-соединение и серверная проверка прав пользователей. Эти меры повышают надёжность системы и обеспечивают сохранность библиотечных данных.
